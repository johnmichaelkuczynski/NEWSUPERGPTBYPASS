GPT BYPASS APPLICATION BLUEPRINT
Prepared as a technical handoff for Grok
Current product URL: https://gptbypass.ink


PURPOSE OF THIS DOCUMENT

This document describes the application as it currently exists. It is intended to let Grok recommend narrowly targeted improvements without guessing about the architecture or replacing working functionality.

Important constraints for any recommendations:

1. Preserve the existing interface unless a specific change is requested.
2. Preserve every working feature.
3. Do not replace Passport.js Google OAuth with Clerk, Replit Auth, Auth.js, or another authentication system.
4. Do not place login in front of anonymous prospects. The application must remain viewable and usable before login.
5. Do not begin payment or Stripe work unless explicitly requested.
6. The central product goal is richer, nuanced rewriting modeled on selected writing samples while preserving the source meaning.
7. Recommendations should distinguish prompt tuning, model selection, pipeline changes, interface changes, security changes, and infrastructure changes.


1. PRODUCT SUMMARY

GPT Bypass is a full-stack web application for rewriting text.

The user supplies:

1. Input Text in Box A.
2. An optional Style Sample in Box B.
3. An optional Content Reference in Box C.
4. Optional instruction presets.
5. Optional custom instructions.
6. A selected language-model provider.

The application sends these inputs to a selected AI provider. The resulting rewrite appears in Box D. GPTZero scores can be displayed before and after rewriting.

The application also supports:

1. File uploads.
2. Stored writing samples.
3. Long-text chunk selection.
4. Re-rewriting a previous output.
5. Exporting output as TXT, DOCX, or PDF.
6. A multi-provider chat interface.
7. Direct Google OAuth.
8. Visit analytics for an administrator.

3. PRIMARY USER FLOW

Step 1:

The user types or uploads source prose into Box A.

Step 2:

The client sends the text to POST /api/analyze-text or uses the upload response. The server asks GPTZero for an AI score and creates chunks for text longer than 500 words.

Step 3:

The user may choose chunks, select one or more instruction presets, select a stored writing sample, paste a custom style sample into Box B, add a content reference to Box C, or enter custom instructions.

Step 4:

The user selects Zhi 1 through Zhi 5 and presses Humanize.

Step 5:

The client sends a RewriteRequest to POST /api/rewrite.

Step 6:

The server scores the source with GPTZero when the source is between 1 and 150,000 characters.

Step 7:

The server creates a rewrite job with processing status.

Step 8:

The AI provider service constructs one rewrite prompt and calls the selected provider.

Step 9:

The server removes Markdown-like markup from the returned text.

Step 10:

The server scores the output with GPTZero when the output is between 1 and 150,000 characters.

Step 11:

The server stores the output, output score, and completed status.

Step 12:

The client places the output into Box D and displays the score.

Step 13:

The user can re-rewrite the previous output, copy it, or download it.

6. API SURFACE

POST /api/upload

Accepts one multipart file under the field name file.
Maximum file size is 50 megabytes.
Validates and extracts text.
Stores a document record.
Requests a GPTZero score.
Creates 500-word chunks when needed.
Requests GPTZero scores for every chunk.
Returns the document, chunks, overall score, and needsChunking flag.

POST /api/analyze-text

Body includes text.
Returns aiScore, wordCount, chunks, and needsChunking.

POST /api/rewrite

Body follows RewriteRequest.
Requires inputText and provider.
Creates a rewrite job.
Calls the selected AI provider.
Cleans markup.
Scores the output.
Stores the completed result.
Returns rewrittenText, inputAiScore, outputAiScore, and jobId.

POST /api/re-rewrite/:jobId

Retrieves the previous completed job.
Uses the previous output as the new input.
Retains the original style sample, content reference, and mixing mode.
Allows current custom instructions, presets, or provider to override stored values.
Creates a new job and returns the new rewrite and score.

POST /api/set-keys

Accepts provider-key values and writes them into process.env at runtime.
This endpoint is currently not protected, does not persist values, and should be treated as a security risk.

POST /api/download/:format

Supported formats are pdf, docx, and txt.
Accepts content and an optional filename.
Returns a generated file.

POST /api/chat

Sends chat messages to a selected provider with optional application context.

POST /api/writing-samples/upload

Accepts a writing-sample file and stores its extracted text.

GET /api/writing-samples

Returns stored writing samples.

POST /api/admin/import-writing-samples

Bulk-imports writing samples from the project writing_samples directory.
The route name says admin, but authorization should be verified before relying on that label.

GET /api/auth/google

Begins direct Google OAuth.

GET /auth/google

Alias for beginning direct Google OAuth.

GET /auth/google/callback

Primary Google OAuth callback.

GET /api/auth/google/callback

Alias for the Google OAuth callback.

GET /api/auth/user

Returns the current authentication state and user.

GET /api/auth/me

Returns the current user identity.

POST /api/auth/logout

Logs the user out and destroys the session.

GET /api/admin/visits

Returns visit analytics and is protected by the isAdmin middleware.

10. CURRENT REWRITE PROMPT

The prompt-building sequence is:

1. Tell the model to rewrite the source so its style matches the supplied style sample at a granular level.
2. If Box B is empty, substitute a hardcoded default style sample based on a Raven Paradox essay.
3. If Box C has content, tell the model to judiciously integrate relevant ideas, examples, and details from that content reference.
4. Expand selected presets into additional rewrite instructions.
5. Append custom instructions.
6. Append the source under Text to rewrite.

The current prompt does not use a separate system message for rewriting.

The source text, style sample, content reference, and instructions are interpolated directly into one user prompt.

The mixingMode value is accepted and stored, but the core prompt primarily decides behavior from whether styleText and contentMixText are present.

The default style sample is long and consumes a significant part of the context window.

The prompt does not currently require an explicit semantic-preservation check, fact lock, quotation lock, citation lock, or named-entity comparison after generation.

Current defect:

The server registry contains duplicate object keys for:

One aside
Asymmetric emphasis
Topic snap

JavaScript silently keeps the later definition. The build reports warnings for these duplicates.

More important defect:

The client preset registry and server preset registry do not consistently use the same identifiers. Unknown selections are silently ignored by the server. This means the interface can show a preset as selected even though it contributes no instruction to the model.

Fine-tuning recommendations should prioritize one shared, validated preset registry used by both client and server.


12. STYLE SAMPLE AND CONTENT REFERENCE

Box B supplies prose whose style should be imitated.

Box C supplies ideas, examples, or details to blend into the rewrite.

The left sidebar loads stored writing samples from the database.

A selected writing sample can populate the style flow.

Long stored samples expose beginning, middle, and ending excerpts.

Risk:

Sending very long style samples and content references can consume the model context, reduce instruction adherence, and increase latency and cost.

Potential tuning direction:

Create a style-profile extraction stage that converts a long sample into a compact, structured style representation before rewriting. The profile could represent sentence-length distribution, clause structure, transition habits, lexical register, hedging, emphasis, paragraph shape, parentheticals, rhetorical patterns, and recurring disfluencies. The rewrite stage would consume the compact profile rather than the entire sample.

Any such extraction must preserve the current ability to use the original sample and should be evaluated against direct full-sample prompting.


13. GPTZERO INTEGRATION

GPTZero is used to score:

1. Uploaded source text.
2. Pasted source text.
3. Long-text chunks.
4. Rewritten output.
5. Re-rewritten output.

The server avoids GPTZero scoring outside the 1-to-150,000-character range for rewrite requests.

Current risk:

Batch chunk analysis uses parallel requests without an explicit concurrency limit. Large inputs can create a burst of GPTZero requests.

Current product limitation:

GPTZero is the only automated evaluator. There is no independent measurement of:

1. Meaning preservation.
2. Factual consistency.
3. Named-entity preservation.
4. Citation preservation.
5. Writing quality.
6. Style similarity.
7. Grammar.
8. Plagiarism or overly close imitation.

A lower detector score alone is not enough to establish a better rewrite.


14. LONG-DOCUMENT PROCESSING

The chunker uses:

500 words per chunk.
50 words of overlap.

Chunks receive IDs, start and end word positions, and optional GPTZero scores.

The interface lets the user choose chunks.

Critical current limitation:

The normal rewrite endpoint does not independently rewrite each selected chunk and reassemble the document. The client concatenates selected chunk contents and sends them as a single rewrite input. Overlapping text can therefore be duplicated.

The rewrite job stores selectedChunkIds, but chunks are currently stored as an empty array in the normal and re-rewrite routes.

The current behavior does not implement a complete long-document continuity system.

Recommended tuning problem:

Design an ordered chunk pipeline that:

1. Splits at paragraph and sentence boundaries rather than only word counts.
2. Uses controlled context overlap without duplicating final text.
3. Creates a document-level style and fact ledger.
4. Rewrites chunks sequentially or with bounded parallelism.
5. Preserves names, claims, quotations, citations, numbering, and cross-references.
6. Reassembles text deterministically.
7. Runs a final continuity and duplication check.
8. Exposes progress and partial failure clearly.


15. RE-REWRITE BEHAVIOR

Re-rewrite uses the previous output as its new input.

It inherits:

styleText
contentMixText
mixingMode
stored custom instructions unless overridden
stored presets unless overridden
stored provider unless overridden

It creates a new rewrite job and obtains another GPTZero score.

There is no automatic loop, target score, maximum attempt policy, semantic drift check, or quality comparison between attempts.

Potential tuning direction:

Treat re-rewrite as a controlled optimization step. Compare meaning, factual integrity, style similarity, and readability before accepting a later attempt. Never optimize detector score alone.

18. CHAT INTERFACE

The chat panel is separate from the primary rewrite workflow.

It maintains an independent provider selection rather than automatically sharing the main provider state.

It can receive application context and send returned content to Input, Style, Content, or Output boxes.

Tuning question:

Decide whether chat is a supporting editor for the rewrite workflow or a separate general assistant. Its purpose should be made explicit before changing prompts or provider behavior.


19. CURRENT ERROR HANDLING

Most server routes use try and catch and return status 500 with error.message.

Most client mutations display toast notifications.

Rewrite jobs are marked failed when provider calls fail.

Current weaknesses:

1. No consistent typed error envelope.
2. No request ID visible to the user.
3. No provider timeout policy described at the route level.
4. No exponential retry or circuit-breaker behavior.
5. No per-provider health status.
6. No explicit distinction between configuration, quota, timeout, validation, provider, detector, and database errors.
7. Error messages may expose low-level provider details.


20. SECURITY AND PRIVACY RISKS

Highest priority:

POST /api/set-keys is unprotected and mutates server environment variables at runtime.

Other issues to investigate:

1. Confirm that every administrative route uses authorization middleware.
2. Add strict request validation with Zod to all mutation routes.
3. Add rate limiting to rewrite, analysis, upload, chat, login, and import routes.
4. Add CSRF protection or equivalent same-site controls for state-changing authenticated routes.
5. Validate filenames and generated download names.
6. Define retention and deletion policies for source text, outputs, uploads, emails, and visit records.
7. Avoid logging full user text or credentials.
8. Fail explicitly when provider secrets are absent; never use default_key.
9. Define account ownership before exposing rewrite history.
10. Review the 50-megabyte request and upload limits for denial-of-service risk.

25. ONE-PARAGRAPH ARCHITECTURE SUMMARY

GPT Bypass is a React and TypeScript single-page application served by an Express and TypeScript backend. The browser manages four text areas, presets, writing samples, chunk selection, scores, provider choice, downloads, chat, and Google sign-in. The server stores documents, writing samples, rewrite jobs, users, and visits in Neon PostgreSQL through Drizzle ORM. A rewrite request is scored by GPTZero, converted into one provider prompt containing a style sample, optional content reference, presets, custom instructions, and source text, sent to one of five AI providers, cleaned, scored again by GPTZero, stored, and returned to the browser. The most important tuning opportunities are to unify the preset registry, create explicit semantic and factual safeguards, develop a compact style-profile stage, implement real long-document rewrite and reassembly, add quality measurements beyond GPTZero, secure the runtime key endpoint, normalize provider errors and fallback behavior, and add regression tests before changing the working user flow.
